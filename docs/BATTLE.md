# 対戦モード — 設計と、なぜそうしたか

このドキュメントは「何を作ったか」より **「なぜその形にしたか」** を残すためのものです。
半年後に読み返して、判断をやり直せるようにしてあります。

---

## 1. 前提：Cloud Functions が使えない

Firebase の **Spark（無料枠）** で動かすことが条件です。
つまり **サーバー側のコードが1行も書けません。**

これがこの設計のほぼすべてを決めています。

普通のリアルタイム対戦は、サーバーが

- 問題を配る
- 正解を持っている（クライアントには渡さない）
- 「誰が先に押したか」を判定する
- スコアを計算して保存する

をやります。今回はこれが**全部できません**。

代わりに使えるのは次の2つだけです。

1. **Firestore のルール** — 「この書き込みを許すか」だけを判断できる
2. **両者が同じ計算をして、食い違いを検出する仕組み** — 相互監視

### 何を諦めたか（正直に）

**正解は クライアントの JS の中にあります。** 隠せません。
ビルド後のファイルを読めば、答えは全部見えます。

これを隠す方法はサーバーを持つ以外にありません。
なので **「答えを隠す」ことは最初から諦め、
「不正しても割に合わない」形にする** 方針にしました。

具体的には後述の

- レート変動の上限（1試合±60）をルールで強制
- 同じ試合の結果を二重反映できない
- 相手の回答は書き換えられない

によって、「1試合で得られる利益」を小さく固定しています。
1回不正しても最大+60、それをやるためにビルド出力を読んで
コンソールを叩く手間がかかります。**手間に対して得が小さい**ので、
現実的には起きません。

そして最も重要なことですが、**対戦のレートは学習量ランキングとは
完全に別のコレクション**です。対戦で不正をしても、
今までのランキングの数字は1つも動きません。

## 2. 最大の設計判断：早押しにしない

### みんはや型（早押し）を採用しなかった理由

「先に押した人が答える」方式は、**通信の速さで勝敗が決まります。**

- 家の Wi-Fi が速い人が勝つ
- スマホの電波が悪い教室では常に負ける
- サーバーがないので「本当に誰が先か」を公平に決める場所がない

学習アプリでこれをやると、**知識ではなく回線で決まる**という
一番やってはいけない形になります。

### 採用した形：時間窓型

```
  問題が出る（両者同時）
       ↓
  ┌──────────────── 20秒 ────────────────┐
  │  両者がそれぞれのペースで答える        │
  └───────────────────────────────────────┘
       ↓
  両者の回答が揃う（または時間切れ）
       ↓
  次の問題へ
```

- 締切時刻（`deadlineAt`）は **1問につき1回だけ**書かれる
- 各端末はその時刻から**自分でカウントダウンする**
- 相手より遅く画面が表示されても、**締切は同じ**

### 速さは「点数」にだけ影響する

早く答えれば速さボーナス（最大50点）が付きます。
ただしここに仕掛けがあります。

```typescript
export const SPEED_GRANULARITY_MS = 500;
```

**残り時間を500msごとの段に切り下げてから**点数にしています。

なぜか。回線の揺らぎは普通 数十〜数百ms です。
1ms単位で点数を出すと、**同じ速さで押した2人に差が付いてしまう**。
500msの段にまとめてしまえば、揺らぎの範囲では**点差がゼロ**になります。

段の幅を大きくしすぎると速さボーナスが意味を失うので、
「揺らぎは吸収するが、実力差は残る」500msにしました。
（`tests/battleCore.test.ts` が、同じ段なら同点・段をまたげば差が付くことを固定しています）

## 3. スコアを Firestore に保存しない

### 保存するもの

回答するとき、Firestore に書くのは**これだけ**です。

```typescript
// 実際の書き込み（パス記法で1問ぶんだけを足す）
answers.{myUid}.q3 = {
  index: 3,                      // 問題番号（キー名と一致していなければ弾かれる）
  choice: 2,                     // 選んだ番号
  panel: [],                     // 並べ替え・組み立てのときの押した順序
  answeredAt: serverTimestamp(), // ★サーバーの時刻★
}
```

**点数は書きません。**

### ★保存形式は「配列」ではなく「マップ」★

`answers[uid]` は配列ではなく、`q0`, `q1`, `q2` … というキーを持つ**マップ**です。
見た目は配列のほうが自然なので、最初は配列で作りました。**それは2つの理由で失敗でした。**

**理由1: Firestore は配列の中の `serverTimestamp()` を受け付けない**

```
FirebaseError: serverTimestamp() is not currently supported inside arrays
```

配列で書こうとすると必ずこの例外になります。
つまり配列版の実装は**1問も回答できませんでした**（詳細は §12 の不具合3）。

**理由2: 配列だとルールから不正を検査できない**

ルールから「この問題にもう答えたか」を配列に対して問うのは、事実上できません。
マップなら `'q3' in answers[uid]` と1行で書けます。
この違いが「後から答えを差し替える」不正を防げるかどうかを分けました。

読み書きの都度、`answerKeyOf(3) → 'q3'` / `answerIndexOf('q3') → 3`
（`src/battle/core/types.ts`）で変換しています。

### ★問題番号はキー名だけを正とする★

同じ番号が中身（`index`）にも入っていますが、**採点はキー名しか見ません**。
キー名はルールで `q{currentIndex}` との一致を強制しているので、中身より信頼できます。

以前は「キー名が読めなければ中身の `index` を使う」という保険を入れていましたが、
**その保険が原因で「正しく答えたのに0点」になる不具合を作りました**（§12 の不具合4）。
保険は外しました。

### なぜか

点数を書けるなら、`score: 999999` と書けてしまいます。
ルールで上限をかけても、上限内の嘘（実際は300点なのに500点と書く）は防げません。

代わりに **両方の端末が、同じ入力から同じ点数を計算します。**

```
  Firestore にあるも（改ざんしにくい）
    ・どの問題が出たか       questionIds（作成後は変更禁止）
    ・何を選んだか           answers[uid].q{i}.choice
    ・いつ答えたか           answers[uid].q{i}.answeredAt（サーバー時刻）
    ・点数の設定             rules（作成後は変更禁止）
       ↓
  battleCore.ts（純関数・両端末で同じコード）
       ↓
  点数（どちらの端末でも必ず同じ値になる）
```

`answeredAt` に `serverTimestamp()` を使っているのが要点です。
端末の時計を変えても、記録される時刻は**サーバーが決めます**。

さらにルール側で **`answeredAt == request.time`** を強制しています。
`serverTimestamp()` を使わず自分で作った時刻を書き込もうとすると、そこで弾かれます。

> ⚠️ この検査は、以前は**コメントだけ書かれていて実際には存在しませんでした**。
> そのため「0秒で回答して速さ満点」が素通りしていました（§12 の不具合5）。

### 食い違いの検出（attest）

計算が確定したら、両者が「自分はこう計算した」を書きます。

```typescript
attest[myUid] = { myScore: 520, opponentScore: 410, outcome: 'win' }
```

2人の申告が食い違ったら、**その試合は無効**にしてレートを動かしません。
片方が改造したコードを使っていれば、必ず食い違います。

「勝ったことにする」改造をしても、相手の申告と合わないので
**レートは付きません**。得をしません。

## 4. 回答形式 — 手打ち入力をゼロにした

利用者の指定は明確でした。

> さすがに手打ち入力は現実見ないので

対戦で「気体の名前を入力してください」をやると、

- スマホのキーボードが出て画面の半分が消える
- IME の変換に時間がかかる（実力と無関係な差）
- 「二酸化炭素」「CO2」「co2」のどれを正解にするかで揉める

ので、**キーボードを使う形式は1つも作っていません。**

### 3つの形式

| 形式 | 見た目 | 元データ |
|---|---|---|
| `choice4` | 4つの選択肢ボタン | もともと4択だった問題 |
| `word` | 4つの語句カード | もともと記述だった問題 |
| `panel` | 文字パネルを順に押す | もともと記述だった問題 |

`word` と `panel` が、記述問題を対戦用に作り替えたものです。

- **`word`**: 正解の語句 + 同じ章から選んだ 3つのダミー語句
- **`panel`**: 正解の文字をバラして並べ、押した順で判定
  （みんはや の文字パネルと同じ操作感。ただし文字数が分かるので `word` より易しい）

`tests/battlePool.test.ts` が **「`choice4` / `word` / `panel` 以外の形式が
1問も混ざっていないこと」** を機械的に検査しています。
生成器を直したときに記述問題が紛れ込んでも、テストで止まります。

## 5. 選択肢を毎回シャッフルしない

利用者の指定です。

> 選択肢は固定でいい。ただ 問題両少なかったらしんどい

### 固定にした理由

選択肢の並びを**生成時に決めて固定**しています。対戦のたびに混ぜません。

混ぜると、部屋IDから決定的に混ぜる必要があります
（両端末で並びが違ったら「3番目を選んだ」が別の意味になる）。
できますが、混ぜる処理が1つ増えるぶん、
**並びがズレる不具合の可能性が増えます。**
そしてズレたときの症状は「正しく答えたのに不正解」という最悪のものです。

固定なら、この不具合は**構造的に起こりません**。

### 「問題が少ないとしんどい」への対応

こちらの懸念のほうが実害があるので、3つ手を打っています。

#### (1) 収録数が少ない教科は出題数を減らす

```typescript
chemistry: {
  questionCount: 7,  // 10問ではなく7問
  note: '収録数がまだ少ないため7問マッチです',
}
```

化学（発展）は46問しかありません。10問出すと1試合で**プールの22%**を消費し、
2〜3試合で既視感が出ます。7問なら15%です。

`tests/battlePool.test.ts` が **「1試合でプールの30%以上を消費する設定を禁止」**
を検査しているので、あとで問題を減らしたときにも気づけます。

#### (2) 同じ小問から作った問題を1試合に混ぜない

化学基礎の763問は、実質**553小問**から作られています。
1つの小問から `word` 版と `panel` 版の2問ができているものがあるためです。

単純に抽選すると、

```
  3問目「次の語を選べ  → 混合物」
  7問目「文字を並べよ  → 混合物」
```

が同じ試合に出ます。**答えを知った状態の2回目はただの作業**です。

`buildQuestionOrder()` が、プール全体をシャッフルしたあと
**同じ小問（グループ）の2問目以降を捨てます**。
「先に絞ってから抽選」ではなく「シャッフル後に間引く」ので、
どちらの形式が採用されるかも部屋IDによって決まり、決定論性は保たれます。

#### (3) 教科カードに収録数を出す

```
  化学基礎    収録763問
  化学        収録46問 · 7問マッチ
```

先に伝えておけば、「同じ問題が出た＝バグ」ではなく
「そういう教科」と理解されます。
黙って少ないほうが不信を招きます。

### 収録数（生成時点）

| 教科 | 収録数 | 1試合 |
|---|---|---|
| 化学基礎 | 763問 | 10問 |
| 生物基礎 | 348問 | 10問 |
| 英語リスニング | 146問 | 8問 |
| 数学 | 100問 | 10問 |
| 英文法 | 100問 | 10問 |
| 化学（発展） | 46問 | 7問 |
| 地理 | 25問 | 5問 |

**合計 1528問。**

リスニングも入れています（利用者の指定「リスニングも入れて。あとから修正するから」）。
リスニングだけ扱いが違います。

```typescript
english_listening: {
  timeLimitOverride: 35,   // 全問35秒に固定
  pointsSpeedMax: 20,      // 速さボーナスを 50 → 20 に下げる
  formats: ['choice4'],    // 4択のみ
}
```

音声の再生が終わるまで答えられないので、
**問題文を読む速さで秒数を見積もる他教科とは前提が違います**。
また読み上げ速度が端末ごとに違うため、速さボーナスを下げて
「端末が速い人が有利」になりにくくしました。
正解の価値（100点）は他教科と同じなので、**聞き取れるかで決まります**。

## 6. 制限時間を問題ごとに変える

利用者の指定です。

> 制限時間は問題ごとに変えて。`src/utils/scoring.ts` のロジックを参考に

既存の `scoring.ts` は「問題文の長さ・選択肢の数」から
想定所要時間を見積もっています。同じ考え方を使いました。

実測の結果（1528問）:

| | 秒数 |
|---|---|
| 最短 | 13秒 |
| 中央値 | 17秒 |
| 最長 | 30秒 |

`tests/battlePool.test.ts` が **8〜40秒の範囲外を禁止**しています。
8秒未満は読み終わりません。40秒超は対戦のテンポが壊れます。

そしてルール側でも締切に上限をかけています。

```
&& request.resource.data.deadlineAt < request.time + duration.value(60, 's')
```

**60秒より先の締切は Firestore が受け付けません。**
改造して「制限時間10分」にすることはできません。

## 7. フレンド対戦を主役にした

利用者の指定です。

> フレンド対戦も可能にして。むしろそれをメインにして

`BattleHome` の並びがそのまま優先順位です。

```
  ┌─────────────────────────────┐
  │  部屋をつくる                │  ← いちばん大きい
  │  合言葉を友だちに送る        │
  └─────────────────────────────┘
  ┌─────────────────────────────┐
  │  合言葉で参加する            │
  └─────────────────────────────┘
  ┌─────────────────────────────┐
  │  相手をさがす（全国）        │  ← 小さめ
  └─────────────────────────────┘
```

### なぜフレンド対戦が正しい主役なのか

全国ランダムマッチは **人がいないと成立しません。**
公開直後は必ず「待っても相手が見つからない」状態になります。
それが最初の体験になると、二度と開かれません。

フレンド対戦は **相手を自分で連れてくる**ので、
利用者が1人でもいれば（友だちを誘えば）成立します。

### 合言葉は4文字

```
  A B 2 C
```

`0 O 1 I L` を**除いてあります**。
口で伝えるとき「ゼロかオーか」で必ず揉めるためです。

紛らわしい文字を除いた 31文字から4文字なので約92万通り。
`battle_codes` は **一覧取得（list）をルールで禁止**しているので、
総当たりしないと他人の部屋は見つけられません。

これは既存の `friend_codes` と同じ考え方です。

### 全国対戦でも45秒待ったら

```typescript
const SUGGEST_FRIEND_AFTER_SEC = 45;
```

45秒相手が見つからなければ、**「フレンド対戦にする」を提案**します。
無言で待たせ続けるのが一番良くないためです。

## 8. ゲスト参加を不可にした

利用者の指定です。

> ゲスト参加は不可（Googleログイン必須）

### 技術的にも、これしかありません

Firestore のルールが判断に使えるのは `request.auth.uid` です。
ゲストには uid がないので、

- 「この部屋の参加者か」を判定できない
- 「自分の回答だけを書いているか」を判定できない
- レートの持ち主を決められない

つまり **ゲストを許すと、ルールで守れるものが何もなくなります。**

`BattleHome` は未ログインのとき、
理由を説明した画面とログインボタンを出します。
黙ってボタンを無効にすると「壊れている」と思われるためです。

そしてルール側でも二重に塞いでいます。

```
function battleSignedIn() {
  return request.auth != null && request.auth.uid != null;
}
```

画面でボタンを隠すだけでは、SDK を直接叩けば書き込めてしまいます。
**「uid が無ければ何も書けない」ことをルールで保証しています。**

## 9. レート（Elo）

```typescript
export const RATING_INITIAL = 1500;   // 初期値
export const RATING_K = 24;           // 1試合の最大変動
export const RATING_FLOOR = 800;      // 下限
export const RATING_MAX_DELTA = 60;   // ルールで強制する上限
export const FORFEIT_RATING_RATIO = 0.5;  // 途中抜けは半分
```

### K = 24 にした理由

チェスの標準は K=32 ですが、これは「1試合で最大32動く」設定です。
学習アプリの対戦は1試合3〜5分で、**1日に何試合もできます。**
K=32 だと1日で数百動いてしまい、レートが実力を表さなくなります。

K=24 なら1試合±24以内。10試合しても±240程度で、
実力に収束しつつ1試合の重みも残ります。

### 下限 800 の理由

下限がないと、負け続けた人のレートが際限なく下がります。
数字が3桁を割ると**心理的に戻ってこられません**。
800で止めておけば「ここから上げよう」と思えます。

### RATING_MAX_DELTA = 60 の役割

これは**ルール側に書いてある数字**です。

```
&& request.resource.data.rating <= resource.data.rating + battleRatingDelta()
&& request.resource.data.rating >= resource.data.rating - battleRatingDelta()
```

K=24 なので、正常な1試合の変動は最大24です。
60まで許しているのは**計算誤差と将来のK値変更に余裕を持たせるため**で、
「1回の書き込みで3000まで上げる」を確実に塞ぐことが目的です。

`tests/battleCore.test.ts` が、
**5×5×3=75通りの組み合わせで |Δ| ≤ K を確認**しています。
K を変えたときにルールの60を超えないか、ここで気づけます。

### 同じ試合を二重反映できない

```
&& request.resource.data.lastRoomId != resource.data.lastRoomId
```

レートを更新するとき、**必ず `lastRoomId` が変わっていなければ通りません。**
同じ試合の結果を連打してレートを盛る経路が塞がれています。

アプリ側（`applyRatingResult`）もトランザクションで
`lastRoomId === roomId` ならスキップしますが、
**ルールにも同じ条件を書いてあります**。
アプリを改造されてもここは通りません。

### 途中抜け（forfeit）

抜けた側の負け・残った側の勝ちにしますが、**変動は半分**です。

通信が切れただけの人を満額で罰するのは不当ですし、
逆に「勝てそうにないときは抜ける」を無罰にもできません。
半分がその折衷です。

## 10. Firestore ルールの構造

### 追記のみ、既存818行は1文字も変えない

新しいヘルパーはすべて `battle` で始まります。

```
battleSignedIn()   battleIsPlayer()   battleUnchanged()
battleValidNewRoom()   battleCoreFixed()   battleStatusStep()
battleIndexForward()   battleDeadlineSane()   battleRatingDelta()
battleAnswersOnlyMine()   battleAttestOnlyMine()   ...
```

既存の `isDocOwner` / `isMyFriend` / `isValidRankingIdentity` などと
**名前が衝突しません**。再利用しているのは `isAuthenticated()` と `isOwner()` の2つだけです。

### 部屋のルール — 何を凍結しているか

```
battleCoreFixed():
  id / subject / joinCode / hostUid / questionIds / rules / createdAt
```

作成後は**この7つを一切変更できません**。

とくに **`questionIds`** と **`rules`** が重要です。

- `questionIds` が変えられると、**自分だけ簡単な問題に差し替え**られます
- `rules` が変えられると、**1問1万点の設定に書き換え**られます

どちらも試合の途中でも変えられません（テストで確認済み）。

### 相手の回答を触れない仕組み

```
battleAnswersOnlyMine():
  answers のキーは players の2人だけ
  かつ 相手のスロットが変更前と完全に一致していること
```

自分の回答は書けますが、**相手の `answers` スロットは
1文字でも変わっていたら書き込み全体が拒否されます。**

これがないと、負けている側が相手の答えを不正解に書き換えられます。
`attest`（結果申告）と `profiles`（表示名・レート）にも同じ仕組みを入れています。

### 自分の回答の中身を検査する（不正防止の本体）

相手の欄を守るだけでは足りません。**自分の欄に嘘を書けたら同じことです。**

```
battleMyAnswerAdded():
  status == 'playing'                                  対戦中しか回答できない
  変化したキー == ['q{currentIndex}']  ちょうど1つ      ★下記3つを同時に封じる★
  q{currentIndex} が元に無かった                        差し替えを封じる
  request.time < deadlineAt                            時間切れ後を封じる
  answeredAt == request.time                           時刻の偽装を封じる
```

`diff().affectedKeys()` は「増えた・消えた・変わった」キーを全部返します。
それが**今の問題ぴったり1つ**であることを求めるだけで、

- 先回り回答（`q5` を今のうちに置く）
- 後出し・差し替え（`q0` を書き換える）
- 過去の回答の削除（`q0` を消してやり直す）

が**同時に**塞がります。

> ⚠️ この検査は、以前は**コメントだけあって実装が無く**、
> 上の不正が全部素通りしていました（§12 の不具合5）。

### 離脱の記録（`left`）も自分ぶんだけ

```
battleLeftOnlyMine():
  変化したキー == [request.auth.uid]  ちょうど1つ
  値 == request.time
  元に無かったことを要求（書き換え不可）
  キーは players のみ（膨らませ攻撃を防ぐ）
```

**★この検査は「共通部」に置いてあります★**

`allow update` は (A)〜(D) のどれか1つを満たせば通る構造です。
`left` の検査を (D)（離脱の更新）の枝の中だけに置くと、
攻撃側は**「回答の更新」という別の枝を選べば回避できます**。

```
❌ 枝の中に置く   → 回答のついでに相手の離脱を偽装できる
✅ 共通部に置く   → どの枝を通っても必ず検査される
```

離脱は**即座に不戦勝になる**ので、ここが空いていると
1回の書き込みで勝ちを奪えました（§12 の不具合9）。

### 共通部で必ず守るもの

どの種類の更新でも効く検査です。**ここに置くか枝に置くかを間違えると穴になります。**

| 検査 | 何を防ぐか |
|------|----------|
| `battleCoreFixed()` | 出題・配点・部屋主・教科のすり替え |
| `updatedAt == request.time` | 端末時刻の書き込み |
| `battleFieldsAllowed()` | 知らないフィールドを植える・巨大な文字列で部屋を殺す |
| `battleLeftOnlyMine()` | 相手の離脱の偽装・自分の離脱の消去 |
| `battleSomethingChanged()` | 空更新の連打（画面妨害・無料枠の焼き切り） |

### 状態は前にしか進まない

```
waiting → playing → finished
   ↓          ↓
aborted    aborted
```

- `finished` から `playing` に**戻せません**（決着後のやり直し禁止）
- `playing` から `waiting` に**戻せません**
- `currentIndex` を**小さくできません**（前の問題のやり直し禁止）

`currentIndex` を戻せると、**答えを見てから同じ問題を解き直せます**。

### 部屋を読めるのは2人だけ

```
allow get, list: if battleIsPlayer(resource.data.players);
```

第三者は**対戦中の部屋を読めません**。
読めると、他人の部屋から `questionIds` を抜いて正解を先に調べられます。

## 12. 実際に見つかった不具合（記録）

開発中、テストを書いた段階で**2つの静かな不具合**が見つかりました。
どちらも「速さボーナスが常に0になる」ものです。

### 不具合1: Firestore の Timestamp を受け取れていなかった

```typescript
// 直す前
if (record && typeof record.answeredAt === 'number') {
  timeUsedMs = record.answeredAt - questionStartMs;
}
```

`answeredAt` には `serverTimestamp()` で書いた値が入るので、
読み出すと **Firestore の `Timestamp` オブジェクト**です。`number` ではありません。

つまりこの `if` は**常に false** で、
`timeUsedMs` は常に「制限時間いっぱい」になり、**速さボーナスは常に0**でした。

```typescript
// 直したあと
export function answeredAtMillis(value: unknown): number | null {
  if (typeof value === 'number' && Number.isFinite(value)) return value;
  const stamp = value as { toMillis?: () => number; seconds?: number } | null | undefined;
  if (stamp && typeof stamp.toMillis === 'function') { ... }
  if (stamp && typeof stamp.seconds === 'number') return stamp.seconds * 1000;
  return null;
}
```

### 不具合2: 配列を期待していたが Map が渡っていた

```typescript
// 直す前
questionStarts: number[]
// 中では
const startMs = questionStarts[i] ?? 0;
```

呼び出し側（`useBattleRoom.ts`）は **`Map`** を渡していました。

```typescript
const startsRef = useRef(new Map<number, number>());
```

`Map` を `[i]` で引くと `undefined` です。`?? 0` で 0 になり、
開始時刻が0（1970年）扱いになって、これも**速さボーナスが常に0**でした。

```typescript
// 直したあと
questionStarts: readonly number[] | ReadonlyMap<number, number>
// 中で吸収する
const startAt = (index: number): number => {
  if (questionStarts instanceof Map) return questionStarts.get(index) ?? 0;
  return (questionStarts as readonly number[])[index] ?? 0;
};
```

### なぜ型チェックで捕まらなかったのか

**`tsconfig.json` に `strict` が付いていません。**

```bash
$ grep -c strict tsconfig.json
0
```

そのため

- `answeredAt: unknown` を `number` と比較しても怒られない
- `Map` を `number[]` の位置に渡しても怒られない

`npm run lint`（`tsc --noEmit`）は**0エラーのまま通っていました**。

### この不具合が本番に出ていたら

「速さボーナスが常に0」は**画面上ほとんど気づけません**。

- 正解すれば100点は入る
- 連続正解ボーナスも入る
- 勝敗もつく
- ただ「早く答えても得しない」だけ

利用者は「なんとなく早解きの意味がない」と感じるだけで、
**不具合として報告される形になりません**。何ヶ月も残ります。

### 対策として入れたテスト

```typescript
it('★Firestore の Timestamp（toMillis を持つ）を受け取れる★', () => {
  expect(answeredAtMillis(fakeTimestamp(1700000000123))).toBe(1700000000123);
});

it('★questionStarts に Map を渡しても配列と同じ結果になる★', () => {
  const byArray = scoreBattlePlayer('me', questions, answers, RULE, startsArray);
  const byMap   = scoreBattlePlayer('me', questions, answers, RULE, startsMap);
  expect(byMap.score).toBe(byArray.score);
  // ★そして速さ点が実際に入っていること★
  // （0 === 0 で通ってしまうのを防ぐ）
  expect(byMap.perQuestion[0].speed).toBeGreaterThan(0);
});
```

2つ目の最後の1行が要点です。
「両方0点」でも `toBe` は通ってしまうので、
**実際に点が入っていること**まで確認しています。

### 教訓

**このリポジトリでは、型チェックは安全網になりません。**
`strict` が無いので、`unknown` の扱いと
コレクション型の食い違いは**実行時テストでしか捕まりません**。

対戦モードは Firestore から来る値（`unknown`）を大量に扱うので、
純関数（`battleCore.ts`）に閉じ込めて**そこを厚くテストする**構成にしました。

---

### 不具合3: 配列の中に `serverTimestamp()` を書けず、1問も回答できなかった

**深刻度: 最大（機能が完全に動作しなかった）**

回答を配列で保存する設計にしていました。

```typescript
// 動かなかったコード
answers[uid] = [...previous, { choice, answeredAt: serverTimestamp() }]
```

Firestore はこれを拒否します。

```
FirebaseError: Function updateDoc() called with invalid data.
serverTimestamp() is not currently supported inside arrays
```

**つまり回答ボタンを押すと必ず例外になり、1問も答えられませんでした。**
テストは純関数（`battleCore.ts`）だけを見ていたので、
**採点ロジックは全部緑なのに、機能そのものが動かない**という状態でした。

**なぜ気づけなかったか**

- 純関数テストは Firestore を通らないので、この制限に触れない
- ルールテストは `assertFails` が中心で、「弾かれること」しか見ていなかった
- 実機で1回動かせば即座に分かるが、この環境では実機確認ができない

**対策**

1. 保存形式を配列 → マップ（`q0`, `q1` …）に変更した
2. ルールテストに**正常系**（`assertSucceeds`）を必ず1本置く方針にした
   （禁止テストだけだと「全部拒否」で緑になり、機能停止を見逃す）

**副産物**

マップにしたことで、ルールから「この問題にもう答えたか」を検査できるようになり、
結果的に不具合5（差し替え不正）も塞げました。**制限に合わせたら設計が良くなった**例です。

---

### 不具合4: 壊れたキーが1つあると、正しい回答が捨てられて0点になる

**深刻度: 高（利用者にまったく説明できない0点）**

マップを番号順に並べ直す `indexAnswers()` に、こんな保険を入れていました。

```typescript
// 悪かったコード
const index = answerIndexOf(key) ?? value.index;  // ← キー名が読めなければ中身を使う
if (!byIndex.has(index)) byIndex.set(index, value);
```

親切なつもりでしたが、**JavaScript のオブジェクトは「キーを入れた順」に走査されます。**

壊れたキー（例: `qX` で中身が `index: 0`）が `q0` より**先**に入っていると、

1. `qX` を見る → キー名は読めない → 保険が発動して**0番の枠を取る**
2. 次に本物の `q0` を見る → `byIndex.has(0)` が既に真 → **本物が捨てられる**

結果は「**正しく答えたのに点が入らない**」です。
しかも原因が保険なので、利用者にも開発者にも何も見えません。

**対策**

保険を外し、**キー名だけを正とする**ようにしました。
キー名はルールで `q{currentIndex}` との一致を強制しているので、中身より信頼できます。

回帰テストは**わざと `qX` を `q0` より先に置いて**います
（順序が意味を持つので、順序を再現しないテストでは意味がありません）。

**変異テスト**: 保険を戻すと2件が赤になることを確認済み。

**教訓**

> 「念のための保険」は、**保険が壊れたときの挙動**まで考えていないと害になる。
> このケースでは、保険が無ければ単に「壊れたキーを無視」で正しく動いていました。

### 不具合5: ルールに「検査する」と書いてあったが、検査が存在しなかった

**深刻度: 最大（不正が全部素通り）**

`firestore.rules` の追記ぶんに、こう書いてありました。

```
//   自分のキーは自由に置けるが、
//   answeredAt にはサーバ時刻しか入れられない（下で検査）ので、
//   後から時刻を偽って速度点を稼ぐことはできない。
```

**「下で検査」の検査が、どこにも書かれていませんでした。**

コメントは実行されません。実際に成立していた不正:

| 手口 | 何ができたか |
|------|------------|
| `answeredAt` に過去の時刻 | 「0.0秒で回答」＝**速さボーナス満点** |
| 出した回答を書き換える | 相手の回答を見てから**正解に差し替え** |
| 締切後に回答 | 時間切れでも**後出しで得点** |
| 先の問題に先回り | まだ出ていない `q5` に**答えを置いておく** |

**どうやって見つけたか**

「攻撃側の手口を実際にやってみる」テストファイル
（`tests/battle.exploit.test.ts`）を書いたら、`assertFails` のはずが**成功しました**。

**対策**

`battleMyAnswerAdded()` を実装。要点は
`diff().affectedKeys() == [今の問題のキー].toSet()` の1行で、
先回り・差し替え・過去の回答の削除を**同時に**封じています。

**教訓**

> **ルールのコメントを信じてはいけない。** 検査は必ずテストで実証する。
> このプロジェクトではこの「嘘のコメント」パターンが**3回**起きました（不具合5・7）。

---

### 不具合6: 端末の時計とサーバーの時計を混ぜていた

**深刻度: 高（時計がずれている人は対戦不能）**

締切（`deadlineAt`）を端末時刻から作っていました。

```typescript
// 悪かったコード
const deadlineAt = Timestamp.fromMillis(Date.now() + limitSec * 1000);
```

一方ルールの検査相手は**サーバー時刻**です。

```
deadlineAt > request.time && deadlineAt < request.time + 60秒
```

**時計が60秒以上進んでいる／遅れている端末で何が起きるか**

| ずれ | 症状 |
|------|------|
| 60秒以上進んでいる | 締切が上限を超えて**対戦を開始できない**（「この操作は許可されていません」） |
| 60秒以上遅れている | 締切が過去になり**同じく開始できない** |
| 十数秒遅れている | 画面は「残り3秒」なのにサーバー側では締切超過 → **回答が消える** |

自分の時計が狂っている人には、原因がまったく分かりません。

**対策: `serverClock.ts`（通信を1回も増やさずにサーバー時刻を推定する）**

**追加の通信は一切していません。** 対戦の書き込みは全部
`updatedAt: serverTimestamp()` を含んでいるので、
`onSnapshot` で返ってくる値を**そのまま時刻の観測**として使えます。

```
書き込み送信 ─────────────→ サーバー（ここで時刻が刻まれる）
    ↑ localSentMs                    │
    │                                ↓
    └──────── 確認が返る ←────────────┘
      ↑ localAckMs

推定した時刻 = サーバー時刻 − (往復の中間点)
誤差         = 往復時間 ÷ 2
```

- 往復が5秒を超える観測は**捨てる**（誤差が大きすぎて役に立たない）
- 片道しか分からない観測は「**下限**」としてのみ使う（推定を上げるが下げない）
- 誤差が小さい観測ほど優先し、5分古い観測は新しいものに譲る

ずれが30秒以上のときは画面に注意を出します（黙って壊れるより良い）。

**教訓**

> **時計は2つある。** サーバー時刻と端末時刻を1つの式に混ぜてはいけない。
> 混ぜた瞬間、その式は「利用者の端末設定に依存する」ようになります。

### 不具合7: 圏外で回答すると、成功したように見えて静かに消える

**深刻度: 高（利用者から見て「答えたのに0点」）**

Firestore はオフラインでも書き込みを受け付け、**手元に溜めます**。
さらに `onSnapshot` は溜めた内容を**即座に返します**。

つまり圏外で回答ボタンを押すと:

1. 画面は「解答済み」に変わる（利用者は成功したと思う）
2. 電波が戻る
3. 溜まっていた書き込みがサーバーへ飛ぶ
4. **もう締切を過ぎているのでルールが拒否**
5. **回答は無かったことになる**

利用者には「ちゃんと答えたのに0点」としか見えません。

**対策: `connection.ts`**

`snap.metadata.fromCache` が**唯一の信頼できるオフライン判定**です
（`hasPendingWrites` は通常の書き込みでも真になるので使えません）。

- オフラインの間は**そもそも回答させない**（`canSubmitAnswer`）
- 選択肢を押せないようにし、薄く表示する（`locked`）
- 「通信が切れています。電波が戻るまで解答できません」と**理由を出す**

**あわせて直したもの**

`!snap.exists() && fromCache` を「部屋が消えた」と扱っていました。
**手元の控えが空なだけ**なので、電波が悪い人を対戦から追い出していました。
今は判定を保留します。

### 不具合8: トンネルに入った人を「逃げた人」として処理していた

**深刻度: 中（無実の人のレートが下がる）**

「無回答が3問続いたら離脱と見なす」としていました。
**1問10〜20秒なので、3問は30〜60秒です。**

地下鉄・トンネル・エレベーターの圏外は普通に30〜60秒あります。
つまり**電車で対戦した人が、席を立ってもいないのに不戦敗**になっていました。

**対策**

1. しきい値を**3問 → 5問**に伸ばした
2. 明示的な離脱（アプリを閉じた等）は `left` に記録され、**即座に**決着する
   （推測に頼らない経路を用意したので、推測側は慎重にできる）
3. **自分がオフラインのときは推測しない**
   自分の電波が悪いだけで相手が消えて見えるため

```typescript
if (hasLeft(leftMap, opponentUid)) return true;   // 明示的な離脱は即決着
if (connection === 'offline') return false;       // 自分が圏外なら推測しない
```

### 不具合9: 相手の離脱を偽装して、不戦勝を1回の書き込みで奪えた

**深刻度: 最大（レートを自由に操作できた）**

不具合8の対策で `left` に「明示的な離脱は即決着」を入れました。
**その `left` がルールで一切検査されていませんでした。**

ルールにはこう書いてありました。

```
// (D) 離脱の記録（left.{自分}）
|| (
     battleIsPlayer(resource.data.players)
     && battleUnchanged('players')
     ...
   )
```

ファイル全体を `grep left` すると、**この1行のコメントしか出てきませんでした。**
「自分」を強制する検査は存在しません。不具合5とまったく同じパターンです。

**成立していた不正**

| 手口 | 何ができたか |
|------|------------|
| `left.{相手}` を書く | **1回の書き込みで勝ちが確定**、相手のレートを削る |
| 回答と同時に `left.{相手}` を書く | 上と同じ。かつ普通の回答に見える |
| 自分の `left` を消す | 逃げた事実を消して**レートを失わずに逃げ続ける** |
| 嘘の時刻を書く | 離脱時刻をずらして判定を操作 |
| 参加者外の uid を大量に書く | ドキュメント1MiB上限に到達させ、**部屋を書き込み不能に** |

しきい値のある推測経路（5問）と違い、**猶予がゼロ**なので実害が最大でした。

**対策**

回答マップと同じ考え方をそのまま適用しました。

```
・変化したキーが request.auth.uid ちょうど1つ
・値は request.time そのもの（端末時刻を書けない）
・元に無かったことを要求（書き換え不可）
・キーは参加者のみ（膨らませ攻撃を防ぐ）
```

**★重要な設計判断: 検査を「枝の中」ではなく「共通部」に置いた★**

`allow update` は (A)〜(D) のどれか1つを満たせば通ります。
`left` の検査を (D) の中だけに置くと、
攻撃側は**「回答の更新」という別の枝を選べば回避できます**。

```
❌ (D) の中に置く   → 回答と同時に相手の離脱を偽装できる
✅ 共通部に置く     → どの枝を通っても検査される
```

「回答のついでに相手の離脱を書く」テストを専用に置いてあります。

**変異テスト**: 検査を外すと**9件が赤**になることを確認済み。

### 不具合10: 相手の表示名を書き換えられた／知らないフィールドを植えられた／空更新を連打できた

不具合9を調べる過程で、更新時の検査に**3つの穴**が見つかりました。

**(a) `profiles` が更新時に無検査だった**

作成時だけ検査していて、更新時は見ていませんでした。

- 相手の**表示名を書き換える**（結果画面と履歴に残るので嫌がらせが成立する）
- 相手の表示レートを 9999 にする
- 巨大な文字列を入れてドキュメント上限を狙う

回答（`answers`）・申告（`attest`）と同じ「相手の欄を固定する」検査を追加しました。

**(b) 更新時のフィールド名が無制限だった**

`winner: 自分` のような**知らないフィールドを自由に植えられました**。
今のアプリは読まないので直接の被害はありませんが、
**将来その名前を使う実装をしたとき、過去に植えられた値を信用してしまいます**。
200KB の文字列を植えて部屋を書き込み不能にすることもできました。

更新後に存在してよいフィールドを許可リストで閉じました。

**(c) `updatedAt` だけの「空更新」が通った**

(B)(C) の枝は「番号が戻っていない」「締切を触っていない」を満たすので、
**何も変えない更新でも条件を全部満たしていました。**

- 部屋が更新されるたび相手の画面が再描画されるので、
  連打すれば**相手の解答操作を妨害できる**（制限時間が10〜20秒なので実害）
- Firebase 無料枠の1日の書き込み上限を焼き切り、
  **その日は全利用者が対戦できなくなる**

「正しい更新は必ず何かを動かしている」という検査を追加しました。

### 不具合11（見張り側の不具合）: テストが緑なのに、検査は誰にも見張られていなかった

**深刻度: 高（安全網が機能していると誤認していた）**

不具合10(b) の許可リストを追加し、テストも2件書いて緑になりました。
念のため**許可リストを丸ごと外して**再実行したところ、**そのまま緑でした**。

原因は、その2件が「他に何も変えていない更新」だったこと。
不具合10(c) の空更新チェックに**先に落ちていた**ので、
許可リストが働いているかどうかは**一度も試されていませんでした**。

```
テストは緑 → 検査が効いている、とは限らない
        （別の検査に先に落ちているだけかもしれない）
```

**対策**

「**正しい回答に相乗りさせる**」形のテストを2件追加しました。
中身のある更新なので空更新チェックは通過し、
**許可リストだけが唯一の防波堤になります**。

これで許可リストを外すと2件が赤になり、見張りが本当に見張るようになりました。

**教訓**

> 検査を足したら、**その検査を外して赤くなるか**を必ず確かめる（変異テスト）。
> 赤くならないテストは、緑であっても**何も守っていません**。

「見張りが本当に見張っているか」を確かめた記録です。

| わざと壊した検査 | 赤くなったテスト数 |

| 勝敗数の `== 1`（`<= 1` に戻す） | 1 |

全部その後に復元し、緑を確認しています。

### 不具合12: 1試合もせずにレートを上限まで盛れた（★コメントが嘘・2回目★）

**症状**

`src/battle/data/battleRanking.ts` の冒頭コメントには、こう書いてありました。

> 2. ルールで ★試合の相互確認が済んだ部屋IDを要求★ する
>    → 架空の試合では書けない。

**その検査は実装されていませんでした。**
ルールが実際に見ていたのは、これだけです。

```
&& request.resource.data.lastRoomId != resource.data.lastRoomId
```

つまり「**前回と違う文字列**」であれば何でも通ります。

```
1回目: lastRoomId: 'fake_a', rating 1500 → 1560
2回目: lastRoomId: 'fake_b', rating 1560 → 1620
3回目: lastRoomId: 'fake_a', rating 1620 → 1680  ← 交互に使い回せる
```

架空のIDを2つ交互に書くだけで、**1試合もせずに上限（4000）まで到達**できました。

**なぜ変化量の上限（60）では止まらなかったか**

これが設計上の一番の学びです。

> **変化量の上限は「1回あたり」しか縛りません。
> 回数を止めていなければ、上限には何の意味もありません。**

「1回で9999にはできない」ことを確認して安心していましたが、
攻撃者にとっては1回でやる必要がまったくありません。

**対策**

Firestore ルールは `get()` で他のドキュメントを読めます。
`lastRoomId` の指す部屋を実際に読み、次を全部要求しました。

| 要求 | 防いでいること |
|---|---|
| その部屋が実在する | 架空の試合 |
| 自分が `players` に入っている | 他人の試合の便乗 |
| `players.size() == 2` | **1人部屋の自作自演** |
| `status == 'finished'` | 決着前のレート先取り |
| 自分の `attest` がある | 申告なしの反映 |

さらに勝敗数の増加を `<= 1` から **`== 1`** に直しました
（→ 別項の「不具合14」に分けて書きました）。

**★「相手の申告も揃っていること」を要求しなかった理由★**

相手が離脱した場合、相手の申告は永久に来ません。
ここで必須にすると**逃げられた側がレートを反映できなくなり、逃げた方が得**になります。
申告の一致判定はアプリ側に置き、
ルールは「実在する自分が参加した決着済みの試合」までを保証する分担にしました。

**`get()` の課金**

ルール内の `get()` は読み取り1回として課金されますが、
発生するのは**1試合の終了時に1回だけ**なので、無料枠（1日5万）に対して無視できます。

**教訓（2回目なので強く書きます）**

> ★コメントは実行されません。★
> 「〜を要求している」と書いてあるコメントを見たら、
> **それを破るテストを書いて、赤くなることを確かめる**。
> 同じ型の事故（不具合5＝`answeredAt` の検査なし）が既に1回起きていたのに、
> 別の場所で再発しました。

### 不具合13: 相手の申告を見てから自分の申告を書き換えれば、常に勝てた

**症状**

レートは「両者の申告（`attest`）が一致したときだけ動く」設計です。
ところがルールは、申告について「**相手の欄が変わっていないか**」しか見ていませんでした。

解答（`answers`）は `battleMyAnswerSane()` で中身まで検査していたのに、
**申告は自分の欄に何を何回でも置けた**のです。

一番効く手口がこれです。

1. 負ける。自分は正直に `outcome: 'lose'` と申告する
2. 相手の申告（`'win'`）が部屋に入るのを**購読で見る**
3. 自分の申告を `'win'` に**書き換える**
4. 相手も `'win'`、自分も `'win'` → アプリ側の一致判定を通過

これで**どんな試合でも勝ちを確定**できます。
相互確認という仕組み全体が無意味になっていました。

ほかに、`at` に過去の時刻を書く／`outcome` に知らない文字列を書く／
点数を `99,999,999` にする／200KBの文字列を混ぜる、も全部通りました。

**対策**

解答と同じ考え方にそろえました（`battleMyAttestSane`）。

- 1回の更新で変えられるのは**自分の欄1つだけ**
  （`diff().affectedKeys() == [自分].toSet()`）
- **まだ自分の申告が無いときだけ書ける**（`!(自分 in 旧attest)`）
  ← これが「後から書き換える」を封じる本体
- `at == request.time`（端末時刻を書けない）
- `outcome` は3種類のみ、点数は数値で上限つき、キーは4つだけ

**教訓**

> 似た性質のデータ（解答と申告）で、**片方だけ厳しく検査していた**。
> 「自分の欄だから自由」ではなく、
> **「他人が見てから直せる」なら順序が武器になる**と考える。

### 不具合14: `<= 1` と書いたせいで「0件」も許してしまった

**症状**

レート反映の更新では、勝ち・負け・引き分けの増加数の合計を検査していました。

```
&& (wins増) + (losses増) + (draws増) <= 1
```

意図は「1回の反映で増えるのは1つだけ」でした。
ところが `<= 1` は **合計 0 も許します**。

```
wins/losses/draws は一切増やさない
rating だけ +60、lastRoomId だけ差し替える  ← 通る
```

勝敗数（表示される戦績）はまったく動かないので、
**見た目には何の痕跡も残らないまま、レートだけが上がり続けました。**

**対策**

```
&& (wins増) + (losses増) + (draws増) == 1
```

`== 1` にしただけです。
これで「レートが動くなら、必ず勝敗数のどれかが1つ増えている」が保証されます。

**教訓**

> ★不等号（`<=`, `>=`）は、それ自体が不具合の型です。★
> 「1より多くない」を書いたつもりで「0でもよい」と書いていました。
> 上限を書くときは必ず**下限も同時に決める**か、
> `==` で書けないかを先に考える。

この検査を `<= 1` に戻す変異テストでは、
落ちたテストが**1件だけ**でした（表 参照）。
「1件しか見張っていない検査」は、それだけ気付かれにくいということでもあります。

### 不具合15: 架空の履歴を大量に書いて、無料枠を焼き切れた

**症状**

履歴（`battle_history`）は自分しか読めないので、
「捏造しても他人に迷惑は掛からない」と考えて形の検査だけにしていました。

**教訓**

> 「自分しか読めないデータ」でも、**書き込み回数は共有資源**。
> 私的なデータだから緩くしていい、とは限りません。

### 不具合16: フレンド対戦に一切入れなかった（★公開直後に発覚★）

これは**テストが全部緑のまま本番だけが壊れていた**例で、
今までの15件と性質が違うので詳しく残します。

**症状**

合言葉を入れると、必ず

> この操作は許可されていません。部屋がすでに閉じている可能性があります。

つまり **フレンド対戦がまったく機能していませんでした**。
フレンド対戦は §7 で「主役」と決めた入口なので、実質全滅です。

**原因**

ルールの読み取り条件がこれでした。

```javascript
allow get: if battleIsPlayer(resource.data.players);   // 参加者だけ
```

一方クライアントは、入室の前に**部屋を読みます**。

```typescript
await runTransaction(db, async (tx) => {
  const snap = await tx.get(roomRef);        // ← ここで拒否されていた
  if (players.includes(uid)) return;         // 再入室の判定
  if (status !== 'waiting') throw …          // 開始済みの判定
  if (players.length >= 2) throw …           // 満員の判定
  tx.update(roomRef, { players: [...players, uid], … });
});
```

**これから入る人は、まだ `players` に居ません。**
だから読み取りが必ず失敗し、
正しく書けていた入室の update（`battleJoining`）に**到達できませんでした**。

なお `tx.get` を消せば読み取り拒否は起きませんが、それは駄目です。
人数を確認せずに書くと、3人目の同時入室で `players` が3人になり
試合が壊れます（§10 でトランザクションにした理由そのもの）。

**なぜ 157 件のテストが緑だったのか（ここが本題）**

参加のテストが `updateDoc` だけを試していました。

```typescript
it('待機中の部屋に2人目として入れる', async () => {
  await seedWaitingRoom();
  await assertSucceeds(updateDoc(doc(ctxFor(GUEST), …), { players: [HOST, GUEST], … }));
});
```

書き込みのルールは正しかったので、これは通ります。
しかし本番は **「読む → 書く」** の2段階で、
★手前の段を誰も試していなかった★のです。

> **教訓**
>
> ルールのテストは「操作の種類」ごとではなく
> **★クライアントが実際に呼ぶ順番★** で書かなければならない。
> 1つの機能が read と write の両方を使うなら、
> 両方を同じ順番で通すテストが必要。
> 「write のテストが緑」は「その機能が動く」を意味しない。

**対策**

1. ルール側：**「待機中で、まだ1人しか居ない部屋」に限って** get を許可。

   ```javascript
   allow get: if battleIsPlayer(resource.data.players)
     || battleOpenForJoin();

   function battleOpenForJoin() {
     return battleSignedIn()
       && resource.data.status == 'waiting'
       && resource.data.players is list
       && resource.data.players.size() == 1;
   }
   ```

   この状態の部屋には**相手の解答も申告も入っていません**
   （`answers` は部屋主の空欄、`attest` は空）。
   `questionIds` は入っていますが、
   ★入室すれば正規の手段で同じものが見える★ので、覗く利点がありません。
   2人揃った瞬間に読めなくなるので、
   §10 の「対戦中の他人の部屋を覗けない」は維持されます。

   **`list` は緩めていません。** get だけです。
   list を許すと、合言葉を知らない人が
   「今開いている部屋」を一覧して割り込めてしまいます。
   部屋にたどり着くには合言葉（31⁴ ≈ 92万通り）が必要なままです。

2. テスト側：**本番と同じ順番**を通すテストを追加（`battle.rules.test.ts`）。

   - 合言葉を引く → 部屋を読む → 自分を足す、の3段を全部実行する
   - 満員の部屋は「読むところから」入れないことを確認
   - 待機中でも `list` はできないことを確認
   - 未ログインは待機中の部屋も読めないことを確認

### 不具合17: 全国対戦が索引不足で動かなかった（★同時に発覚★）

**症状**

- 全国対戦を押すと、画面に**英語のまま**
  `The query requires an index. You can create it here: https://console…`
- さらに、そのエラーが出ない環境でも
  **「対戦相手を探しています」から永遠に進まない**

**原因**

`firestore.indexes.json` が**空**でした。

```json
{ "indexes": [], "fieldOverrides": [] }
```

Firestore は「等式 + 並べ替え」や「array-contains + 等式 + 並べ替え」を
**複合索引なしでは実行できません**。
該当したのは2箇所です。

| 場所 | クエリ | 症状 |
|---|---|---|
| `findOrEnqueue` | `where(subject) + orderBy(createdAt)` | ★英語のエラーが表示★ |
| `watchMatched` | `array-contains + where(status) + orderBy(createdAt)` | ★何も起きない★ |

**なぜ2つ目は気付かれなかったか（こちらが怖い）**

購読のエラー処理が、こうなっていました。

```typescript
() => {
  // 権限や索引のエラーでも待機画面を壊さない
},
```

「画面を壊さない」つもりで書いた**空のエラー処理**が、
実際には **不具合を完全に隠す装置** になっていました。
利用者から見えるのは「いつまでもマッチしない」だけで、
原因を示す情報がどこにも出ません。

> **教訓**
>
> エラーを握り潰す親切は、**不具合を見えなくする**。
> 「画面を壊さない」と「原因を伝えない」は別のことで、
> ★console には必ず残し、利用者にも「失敗した」ことだけは伝える★。

**対策（3段構え）**

1. **★索引が要らない形に書き換えた（これを主軸にした）★**

   Firestore は **条件が1つだけの検索なら索引を自動で作ります**
   （単一フィールド索引。`==` も `array-contains` も対象）。
   手で用意しなければならないのは、条件を**組み合わせた**検索だけです。
   （出典: <https://firebase.google.com/docs/firestore/query-data/index-overview>）

   そこで両方のクエリを「条件1つ」に減らしました。

   - `watchMatched`：`orderBy` と `status` の絞り込みをやめ、
     `array-contains` の1条件だけに。
   - `findOrEnqueue`：`orderBy` をやめ、`==` の1条件だけに。

   並べ替えと絞り込みは手元で行います。
   ここで扱うのは「今この教科で待っている人」「自分が関わる待機中の部屋」
   だけで、同時に数人しか居ないため負荷になりません。
   **「古い順」の公平性（§7）は手元の並べ替えで必ず守ります。**

   > **なぜ索引のデプロイを前提にしなかったか**
   >
   > 索引は `firebase deploy --only firestore:indexes` という
   > **別のデプロイ**が必要で、ルールの公開では作られません。
   > これには開発ツールの導入が必要で、利用者にとって負担が大きい。
   > 実際、公開手順書にこの手順が抜けていたことが今回の事故の原因でした。
   >
   > **手順が増えるほど、抜ける。**
   > だから「手順を正しく書く」より「手順を要らなくする」ほうを選びました。

2. **索引の宣言も入れておいた**（将来のため）—
   `firestore.indexes.json` に2件宣言しました。
   ただし**現状これはデプロイしなくても動きます。**
   将来、対戦人数が大幅に増えて手元の絞り込みが重くなったときに使えます。

   > **★「まず索引つきで試して、失敗したら retry」にしなかった理由★**
   >
   > 一度はその実装にしました（`failed-precondition` を捕まえて再試行）。
   > しかし索引をデプロイしない運用では**毎回1回目が必ず失敗する**ので、
   > 通信が毎回2往復になり、待ち時間とエラーログが無駄に増えます。
   > 最初から索引の要らない形で投げるほうが速く、確実です。

3. **エラーを日本語にした** — `failed-precondition` を
   `friendlyError()` に追加しました。
   英語の内部エラーと**管理コンソールへの URL** を
   利用者の画面に出すのは、分かりにくいだけでなく不適切です。
   詳細は console に残し、画面には日本語の案内だけを出します。

## 13. なぜ `onSnapshot` を1箇所に閉じ込めたか

`useBattleRoom.ts` が **唯一の購読者**です。
UI 側（`BattleRoomScreen.tsx`）は結果を受け取るだけです。

### 分けると壊れる

「待機画面」「対戦画面」「結果画面」を**兄弟のコンポーネント**にして
それぞれで `useBattleRoom` を呼ぶと、

- 画面が切り替わるたびに `onSnapshot` が張り直される
- 各問題の開始時刻を覚えている `startsRef` が**リセットされる**
- 開始時刻を失うと（不具合2と同じ理屈で）**速さボーナスが0になる**

そこで `BattleRoomScreen` が3つの状態すべてを1つのコンポーネントで描いています。

```typescript
// waiting → playing → result を1つのコンポーネントで持つ理由:
// これを兄弟の画面に分割すると onSnapshot が張り直され、
// startsRef（各問題の開始時刻）が失われる。
```

見た目の整理としては分けたほうが綺麗ですが、
**分けると静かに壊れる**ので分けていません。ファイル内にこの理由を書いてあります。

## 17. まとめ：この設計の弱いところ

隠さず書きます。

1. **正解はクライアントにある** — サーバーがないので隠せません。
   「不正しても割に合わない」形にすることで対処しています。

2. **`attest` の食い違いは検出できるが、どちらが嘘かは分からない** —
   なので無効試合にしています。正直な側も損をします。
   ただし損は「レートが動かない」だけです。

3. **`battle_queue` の削除が緩い** — マッチングの取り合いを解決するため、
   ログイン済みなら誰でも他人の待機券を消せます。
   嫌がらせで消し続けることは可能ですが、
   被害は「マッチングし直し」だけで、点数もレートも動きません。

4. **`strict` が無いので型が守ってくれない** — 実際に複数の不具合が出ました。
   純関数に閉じ込めてテストを厚くする、で対処しています。
   対戦モードのファイルだけは `tsconfig.battle.json` で `strict` を効かせて
   監査し、実際に見つかった型の穴を全部直しました。

5. **サーバー時刻の推定には誤差が残る** — `serverClock.ts` は
   往復時間の半分を誤差として持ちます。通信が安定していれば数十ミリ秒ですが、
   極端に遅い回線では誤差が大きくなります。
   誤差が5秒を超える観測は捨てるので**推定が大きく狂うことはありません**が、
   「観測がまだ1回も取れていない状態」では端末時刻のままです。
   対戦開始の書き込みで最初の観測が入るので、実際に問題になるのは
   **1問目の締切だけ**です（そこはルールの60秒上限が保険になっています）。

6. **不戦敗の判定はどうしても推測を含む** — 明示的な離脱（`left`）は
   確実ですが、アプリを強制終了された場合は記録が残りません。
   その場合は「無回答が5問続いたら」という推測に頼ります。
   5問（50〜100秒）待つので**長い圏外を離脱と誤判定しにくい**代わりに、
   **本当に逃げた相手を待つ時間も長くなります**。
   Cloud Functions があれば、サーバー側で接続状態を持てるので正確に判定できます。

7. **「コメントに書いたが実装が無い」事故が3回起きた** —
   `answeredAt` の検査、`left.{自分}` の制限、そして許可リストの見張り。
   ルールのコメントは実行されません。
   **検査を足したら、外して赤くなるかを必ず確かめる**（変異テスト）方針を
   §10 と §12 に記録してあります。

これらは **Cloud Functions を使えるようになれば全部解決します**（1〜3、5、6は特に）。
Blaze に移行する日が来たら、
サーバー側で「問題を配る・正解を持つ・採点する」に移すのが正しい形です。

そのときに書き直しやすいよう、**採点は純関数に完全に分離してあります**
（`battleCore.ts` は Firestore にも React にも依存していません）。
同じコードをサーバー側でそのまま動かせます。
